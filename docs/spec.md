# مواصفات «تأكّد» والقرارات المعتمدة

آخر تحديث: 23 نوفمبر 2026. هذا الملف يجمع القرارات التي اعتمدها صاحب المشروع في مراجعة الفكرة خطوة بخطوة، وهو المرجع عند أي تعارض مع المقترح الأصلي.

## 1. المشكلة والفئة
- **الفئة:** جميع المواطنين والمقيمين في الإمارات، وكل الأعمار. لا توجد فئة أولى خاصة، ولا ميزة «أرسلها لابني».
- **النطاق:** الرسائل والروابط عبر **الواتساب** و**الرسائل النصية SMS** فقط.
- **المواقف الرئيسية:**
  - رسالة شركة شحن تطلب دفع رسوم عبر رابط.
  - إعلان بيع وشراء يرسل رابط دفع ويطلب رقم البطاقة البنكية.

## 2. رحلة المستخدم
1. أول فتح: **اختيار اللغة** (عربي / English)، ثم **صفحة الخصوصية مرة واحدة** مع موافقة. تبقى متاحة برابط داخل التطبيق.
2. إدخال الرسالة بإحدى الطرق:
   - لصق النص (أساسي)
   - إرفاق صورة أو لقطة شاشة (النص يُستخرج داخل الجهاز)
   - تسجيل صوتي (اختياري، إن بقي وقت)
3. الفحص: حجب الحساس، ثم فحص الرابط والنص.
4. النتيجة: الحالة + أسباب + تظليل الكلمات والروابط المشبوهة.
5. الإجراء الآمن + زر «بلّغ عن الرابط».

## 3. الحالات والشرح
| الحالة | متى | الإجراء المقترح |
|---|---|---|
| اشتباه عالٍ `high_suspicion` | عدة إشارات قوية: رابط لا يطابق الجهة، طلب بطاقة أو OTP، استعجال | لا تضغط الرابط ولا تدفع، وبلّغ |
| غير واضح `unclear` | إشارات قليلة أو متضاربة | تحقق من الجهة بنفسك من تطبيقها أو موقعها الرسمي |
| لا مؤشرات ظاهرة `no_visible_indicators` | لم نجد شيئاً، وهذا لا يعني الأمان | الأفضل تفتح تطبيق الجهة بنفسك |

- 3 أسباب كحد أقصى، بلغة بسيطة، بلغة واجهة المستخدم.
- لا تسمية لنوع الاحتيال.
- لا نسبة مئوية للثقة.
- رابط رسمي + نص سليم ⇒ `no_visible_indicators` مع: ما فحصناه (النطاق يطابق الجهة، لا طلب دفع أو رمز)، وما لا نضمنه (مصدر الرسالة نفسه)، ونصيحة فتح تطبيق الجهة بنفسك. لون محايد، ليس أخضر قوياً.
- رابط رسمي + طلب OTP أو بطاقة ⇒ `high_suspicion`.

**أمثلة شرح:**
- AR: «الرسالة تطلب منك إدخال رقم بطاقتك عبر رابط، والرابط لا يشبه موقع شركة الشحن المعلنة، وتحثّك على الاستعجال. لا تدخل بياناتك.»
- EN: "This message asks for your card details through a link. The link doesn't match the shipping company it claims to be, and it pressures you to act fast. Don't enter your details."

## 4. فحص الرابط (نصي، بدون زيارة)
- النطاق الحقيقي مقابل الجهة المدّعاة في النص.
- تشابه خادع (حرف مبدّل/مكرر)، نطاقات فرعية مضللة (`brand.other-site.com`)، punycode.
- مختصرات الروابط، امتدادات غير معتادة، عنوان IP بدل نطاق، غياب HTTPS، طول ورموز غريبة.
- مقارنة بقائمة نطاقات رسمية في `data/` — **تحتاج تحقق** من مصادر رسمية قبل الاعتماد.
- مستقبلاً (ليس في النموذج الأولي): قواعد بيانات سمعة (Google Safe Browsing، PhishTank)، فتح الرابط في بيئة معزولة.
- ممنوع جلب الروابط من الخادم (شروط الهاكاثون + خطر SSRF).

## 5. البلاغ
- شاشة «بلّغ عن الرابط»: نص بلاغ جاهز (الرابط، النص بعد الحجب، وقت الاستلام، القناة واتساب/SMS، إجابة «ماذا حصل؟») + زر «نسخ».
- القناة: **الاتحادية فقط** — منصة eCrime في تطبيق وزارة الداخلية (MoI UAE).
  - مصدر التحقق: https://u.ae/en/information-and-services/justice-safety-and-the-law/cyber-safety-and-digital-security/report-cybercrimes-online (21 نوفمبر 2026).
  - شكل نموذج البلاغ داخل التطبيق وطريقة فتحه برابط مباشر: **يحتاج تحقق**.
- خانة اختيارية «ماذا حصل؟»: لم أضغط الرابط / ضغطت الرابط / أدخلت بيانات بطاقتي / دفعت مبلغاً.
  - «أدخلت بيانات بطاقتي» أو «دفعت مبلغاً» ⇒ أول ما يظهر: «تواصل مع بنكك فوراً لإيقاف البطاقة»، ثم البلاغ.
- التطبيق لا يرسل البلاغ نيابة عن المستخدم. الإرسال المباشر للجهة = خطوة مستقبلية بشراكة رسمية (نقطة قوية في العرض).

## 6. الخصوصية
- أقل بيانات: نص الرسالة فقط. لا اسم، لا هوية، لا حساب، لا تسجيل دخول.
- حجب قبل التحليل: أرقام البطاقات (Luhn)، الهوية الإماراتية (`784-XXXX-XXXXXXX-X`)، أرقام الهواتف، IBAN (`AE..`).
- الصور: OCR داخل المتصفح (tesseract.js، ara+eng)، والصورة لا تغادر الجهاز. جودة القراءة على لقطات الواتساب تحتاج اختباراً.
- لا حفظ افتراضياً. سجلات الخادم بدون نص الرسالة.
- **حفظ اختياري ومعلن** لتحسين النموذج، بموافقة صريحة.
- صفحة خصوصية تظهر مرة واحدة أول فتح، وتذكر: أن النص بعد الحجب يُرسل لخدمة النموذج اللغوي (إن استُخدم API)، وأن الإدخال الصوتي قد يعالجه المتصفح خارجياً.
- الإطار القانوني الإماراتي لحماية البيانات: النص الدقيق **يحتاج تحقق** قبل ذكره.

## 7. التقنيات
- واجهة React متجاوبة، عربي/إنجليزي، RTL/LTR.
- خادم Python + FastAPI.
- نموذج لغوي عبر API لتحليل النية وصياغة الشرح، **بعد الحجب**، مع محرك قواعد.
  - البدائل المستبعدة (توثَّق في README): نموذج محلي مفتوح (أخصّ لكن أضعف وأثقل في وقت الهاكاثون)، مصنّف تقليدي (يحتاج بيانات تدريب لا نملكها).
  - لو توفر وقت: نموذج محلي لخصوصية أعلى.
  - **اسأل المنظمين:** هل الخدمات الخارجية مسموحة؟ هل يوفرون مفاتيح API؟
- الصوت: Web Speech API (اختياري).
- الأولوية: النص والصورة، ثم الصوت.

## 8. القياس
**اختبار تقني (ننفذه نحن على النموذج):**
- 60 رسالة اصطناعية، عربي وإنجليزي، واتساب وSMS: احتيالية بأنواعها، سليمة، ملتبسة، ومنها رسائل OTP سليمة (تسليم رمز).
- المؤشرات: الإنذارات الخاطئة، الفوات، نسبة «غير واضح»، و**اكتشاف طلب البطاقة أو OTP** (نسبة الرسائل الطالبة لهما المصنفة `high_suspicion`)، مع قياس الإنذارات الخاطئة على رسائل تسليم الرمز السليمة.

**تجربة مستخدمين (تصميم، ينفذها الفريق على أشخاص حقيقيين):**
- 60 مشاركاً من أعمار مختلفة، تقسيم عشوائي لمجموعتين: (أ) تستخدم «تأكّد»، (ب) تقرأ نصيحة توعوية عادية.
- كل مشارك: 10 رسائل اصطناعية (6 احتيالية، 4 سليمة).
- المؤشرات: نسبة اختيار الإجراء الآمن، زمن القرار، الإنذارات الخاطئة، وضوح الشرح (1–5)، واكتشاف طلب البطاقة/OTP.
- **لا** نحاكي مشاركين بالذكاء الاصطناعي ونعرضهم كنتائج بشرية. إن لم تُنفذ في الوقت، تُعرض كخطوة تالية.
